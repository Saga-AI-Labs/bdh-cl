## 1. Goal and wall

Graft #2 = grow 1024 -> 1152 (+128 units, +8192 neurons/head, 3.62 B params).
**Purpose decision OPEN** (section 7); the P3 deployment verdict sharpens it:
a third domain adds little while chat serving is broken, so the mask-aware
generation primitive (section 5) is a candidate to outrank - or join - the
growth step.

The wall (report section 12): the 1024 -> 1152 attempt OOM'd at the cap -
95.40 GiB in use, 2.25 GiB short, during the route-aware prefix backward at
b1. Per graft: ~+1.4 GiB weights, ~+2.8 GiB Adam + backup. The per-step
training envelope binds, not the grow moment.

## 2. Option A (recommended): wd-0 backup redundancy - no semantic change

The `elem_frozen_backup` (~11.3 GiB at mult 1024; ~12.9 GiB once old =
65536 neurons/head) exists for wd>0 regimes (F-V9): old and new elements
share ONE tensor in ONE AdamW param group, so per-element decay is
impossible at group level - hence snapshot/restore. At **global wd=0** the
backup is mathematically redundant:

- old-neuron grads are exactly 0 from step 0 of the grown phase (gate masks
  applied every step before the optimizer step) -> m = v = 0 forever ->
  AdamW update exactly 0;
- the decoupled decay branch is guarded at wd == 0;
- zeros stay zeros in bf16; grad-clip norm over zeros is a no-op;
- GradScaler is disabled for bf16 (plain optimizer.step).

That covers the 2.25 GiB shortfall ~5x (frees ~12.9 GiB at graft #2).
Honesty note: the backup is also defense-in-depth against unknown write
paths; removing it trades the mid-run guard for proof + tripwires (the
gates below) - there is no in-run guard anymore if both are wrong.

## 3. Option B: prune/merge between grafts (semantic change; separate probe)

- **B1 (identity-preserving):** prune only in the new segment - erodes
  exactly the fresh competence (S2/S4 territory). Weak candidate.
- **B2 (full prune):** sacrifices the bit-exact story (S1 "== base" becomes
  "measured drift"). This is a DIFFERENT probe (capacity exchange),
  sensible AFTER graft #2, not as its enabler. `prune_eval.py` gives the
  drift forecast; the fullcov instrument makes drift exactly measurable.
- **Merge:** `merge.py` concatenates separately trained models (doubles the
  neuron axis) - a consolidation tool for later/bigger hardware, not for
  a +128 graft.

## 4. Option C: TP=2 (hardware escalation)

Shards the neuron axis across 2 units. On the ReLU path (k_sparse_ratio=0
in every checkpoint) the global-topk problem is moot, but the port remains
a campaign: pair-quantized freqs across shard boundaries, per-device
reduction orders (the ~2e-8 tolerances become device-dependent), mask and
decoder-row semantics. Requires different hardware (the GB10 Spark is one
unit). Escalation path if A + the existing envelope are insufficient.

## 5. Parallel registered work item: mask-aware generation

From the P3 deployment verdict (report section 14, commit 9505ab3):
`generate()` samples unmasked today; chat serving needs zh->old enforced
in generation. Scope: thread the neuron mask through generate(), register
a generation validation cell (zh prompt -> zh output under the old mask;
English legal prompt -> English under full, as the positive control).
Cost ~a day. The efficiency economy (a10ad6b: ~500 effective steps absorbed
the host domain via complement learning) is the registered expectation for
any attach phase in graft #2 - further-domain absorption at the 0.1-weight
schedule is expected to stay in the same order of cost.

**Executed 2026-11-15** (same day, not ~a day): the mask threading landed in
G-A0 (e8b93e1) and the validation cell ran (`scripts/gen_serve_check.py`,
5 samples x 200 tokens per cell). Result reshapes the serving decision: the
registered zh functional failure was prompt-regime-bound (the eval's fixed
ASCII legal prompt); on real zh prompts the full-width model produces
Chinese 5/5 - see the report's second deployment-reading revision (8a0433a).
The chat serving map simplifies to "always full"; zh->old is the
bit-exact-base option, not a functional necessity; the primitive stays as
the drift instrument, and the mixed-content case (English system prompt +
Chinese user content) is the open regime for window-level routing.

## 6. Sequence and costs

**Priority order (operator + Grok review, 2026-11-15):**

1. **Option A now** (G-A0 -> G-A1 -> G-A2, ~1 day): lowest risk, preserves
   the bit-exact isolation story; the real graft stays gated on G-A2 green.
2. **Mask-aware generation next** (section 5, ~1 day): the highest-leverage
   capability - growth without inference-time mask enforcement leaves the
   key invariant unusable for chat.
3. **Decision gate**: serving works cleanly -> proceed to the real graft #2
   with a THIRD domain chosen meaningfully different from zh and legal
   (e.g. code or pure math) to test whether the complement-learning /
   D-cell-collapse pattern generalizes. Memory still tight even with the
   backup off -> stop and reassess (TP or prune).
4. **Real graft run** (~11.7 s/step at 1152; 10000 iters ~ 32.5 h + post-run
   matrix). The post-graft fullcov matrix is mandatory; the S1 identity cell
   is zero-tolerance.
5. B (prune/merge) and C (TP=2) stay contingency, not primary path.

No risk to existing artifacts before G-A2; P1/P3 checkpoints untouched.

**Registered addenda (Grok review):** (a) a tiny-scale backup-ON control

## 7. Gate results (2026-11-15)

### G-A1 PASS (tiny scale; `/tmp/opencode/ga1/ga1.log`)

- **auto -> off at wd=0:** the 8-step P3 smoke train built NO backup
  (`frozen-backup: off | wd=0 restore is a mathematical no-op`); the child

### G-A2 PASS with a corrected memory reading (`/tmp/opencode/ga2_dryrun/`)

- **Dry run 1024 -> 1152** on the P3 last checkpoint (`--grow-mult 128`,
  backup auto -> off, 4 steps, in-loop eval at b1, both checkpoint writes):
  completed under the 97.35 GiB cap, all required prints present, no backup
  built, clean ckpt write.
- **Identity gate BIT-EXACT:** zh fullcov b4 at `--mask-old-mult 1024` on
  the dry-run checkpoint == the P3 zh@0 post cell on all printed digits:
  **val 1.7470 / test 1.6858**. The frozen prefix [0,65536) IS the full P3
  model, preserved bit-exactly WITHOUT the backup. (The eval's own samples
  differ from the registered cell's because samples always run unmasked -
  here over the 1152 model with a 4-step new block; NLLs are the registered
  quantity.) The mask-896 identity (1.7603/1.6980) holds implicitly.
- **Memory correction.** Measured peak: **91.99 GiB allocated / 96.40 GiB
  reserved** - not the ~82-85 the plan predicted. Reconciliation: params are
  fp32 (the bf16 in the train print is the autocast dtype), so states are
  weights 14.5 + grads 14.5 + Adam m+v 29.0 = 58.0 GiB, plus ~34 GiB of b1
  route-split activations at the peak moment. The OOM'd attempt's
  "95.40 in use, 2.25 short" was its FAILURE moment, not its full demand;
  with the 12.0 GiB fp32 backup in its states (~70 GiB total), its demand
  reconstructs to roughly 104 GiB - and 104 - 12.0 = 92 == the measured
  peak. The backup saving is real and sized as designed (12.0 GiB fp32, not
  the plan's rounded ~12.9), but the graft-#2 headroom is **~0.95 GiB
  reserved / ~5.4 GiB allocated** - NOT the ~5x coverage the plan implied.
- **Implication for G-A3:** the per-step profile is stationary and the
  4-step dry run already covers the eval and save moments, so the real run
  fits - but with ~1 GiB reserved headroom over 32 h. An overrun surfaces as
  a clean in-process OOM (cap design) with best-ckpt recovery at <=50-step
  granularity. Optional contingency if it ever OOMs: fused AdamW (removes
  the param-sized denominator temporary at the optimizer step) - requires
  its own mini-gate before use.

### Run command (G-A3; run name `g2_code`)

```
BDH_MEM_FRACTION=0.8 PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True \
python -u -m pipeline.run train \
  --model bdh --dataset textmix \
  --text-mix legal:data/textmix2/legal.txt \
  --text-mix2 code:data/textmix2/code.txt \
  --text-mix-mb 30 \
  --n-embd 1024 --n-head 16 --n-layer 4 --block-size 512 \
  --init-from out_c/routed_probe/bdh_textmix_p3_mixed_last.pt --grow-mult 128 \
  --mixed-alternate --route-aware --route-alpha 0.9 --route-split-backward \
  --learning-rate 1e-4 --weight-decay 0 --frozen-backup auto \
  --warmup-iters 2 --lr-decay-iters 10000 \
  --batch-size 1 --max-iters 10000 --eval-interval 50 --no-compile \
  --out-dir out_c/routed_probe --run-name g2_code
```
