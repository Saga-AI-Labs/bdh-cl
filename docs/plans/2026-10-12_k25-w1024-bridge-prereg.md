# K25/W1024 Bridge — Scaling Probe at Double Width

**Status:** DRAFT v0.3 · drafted 2026-10-12 · measured 2026-10-14 · Quinn
**Purpose:** Isolate whether the BDH mechanism (storage exact, serving degraded, routing repaired) holds at `n_embd=1024` (`n_head=16`) with the same K25 territory mix.
**Hardware:** DGX Spark `spark-d1da` (192.168.178.52), GB10, 3.5 TB free NVMe

> **v0.2/v0.3 correction (2026-10-14):** every parameter, checkpoint and timing figure in v0.1 was
> arithmetic, and the arithmetic was wrong by roughly a factor of nine. v0.2 replaced them with
> measurements. v0.3 corrects one v0.2 *analysis*: the first reading of the memory measurement
> was wrong (see VRAM section); the independent `nvitop` figure confirms the v0.2 projection.

---

## Why This Bridge

The K20/W512 ladder (2× multi-seed) established:
- K3 routing: 99.14–99.18% PASS
- K4 retention: PASS (median ratio 1.0000, max 1.0429)
- Joint/routed gap: 6.76–6.86×
- P5 bit-exact preservation: 25/25 phases PASS

All at `n_embd=512`, `n_head=8`, `head_dim=64`.

**Open question:** does the mechanism survive when the base architecture is wider? This is a
**pure scaling probe** — same territories, same data windows, same protocol, same instrument
suite. The only changed variable is `n_embd` (512→1024) with `n_head` (8→16) so that
`head_dim` stays 64.

## W1024 Base Phase (new — does not exist yet)

K20 initialised from the already-trained A1-K5 bases (W512). The bridge needs its own W1024
base, trained with the **same base protocol**, only the width changes. Verbatim from
`scripts/quinn/ladder_sondeA.sh` (A1-K5 phase 1), with `n_embd`/`n_head` swapped:

```
.venv/bin/python -m pipeline.run train --model bdh --dataset textmix \
  --text-mix "prose:data/textmix/wikitext-103-raw/wiki.train.raw" --text-mix-mb 300 \
  --n-embd 1024 --n-head 16 --mlp-internal-dim-multiplier 128 \
  --block-size 512 --max-iters 150000 --batch-size 4 \
  --warmup-iters 1000 --lr-decay-iters 10000 \
  --run-name "k25w1024-base"
```

The output checkpoint name must carry the `bdh_textmix_` prefix (the Sonde B base/prefix bug).

**Compile setting — open protocol question.** `scripts/quinn/ladder_sondeA.sh` sets
`export TORCHDYNAMO_DISABLE=1`, i.e. Sonde A ran **uncompiled**; the K20 prereg and the K20
results report mention `torch.compile` nowhere. The sibling ladders disagree: `ladder_ra2b.sh`
and `ladder_ra2_resume.sh` also disable dynamo, while `ladder_fixedcap.sh` notes the .200
venv has it enabled by default. **Whether K20 itself ran compiled or not is therefore
undetermined from the repository.** The preflight below measured both, so the choice is a
speed/protocol trade rather than an unknown: compiled is 1.49× (base) to 2.74× (grow) faster,
uncompiled is what Sonde A demonstrably used. This must be decided before phase 1, not assumed,
because it changes the wall clock by a factor of ~2 and the comparability to K20 in a way we
cannot currently check.

**Wall cost — extrapolated, not measured.** The preflight below measured **batch 1**. The base
runs at **batch 4**, which is roughly 4× the per-step cost:

| Basis | Value |
|---|---|
| measured, batch 1, compiled, mult 128 | 437 ms/step |
| scaled to batch 4 (estimate) | ~1.75 s/step |
| 150,000 steps | **~73 h ≈ 3 days** |

Disk for the base: 4.84 GB per checkpoint, `best` + `last` ≈ 10 GB.

## Training Protocol (grow phases)

| Parameter | Value |
|---|---|
| steps per phase | 10,000 |
| `--grow-mult` | 32 |
| `--route-aware` / `--route-alpha` | on / 0.9 |
| `--no-freeze-attn` | on (inert for BDH: attention is parameter-free) |
| optimizer | fresh per phase |
| restore | F-V9 step-end |
| router | likelihood scan (`eval_router`) |
| eval window | 128 |
| crops per domain | 200 |
| `--block-size` | 512 |
| batch | 1 (grow phases), as K20 |

**No hyperparameter search. No protocol drift from K20.**

Grow-phase invocation (verbatim from the smoke, which ran clean):

```
.venv/bin/python -m pipeline.run train --model bdh --dataset textmix \
  --text-mix "legal:data/textmix2/legal.txt" --text-mix-mb 30 \
  --n-embd 1024 --n-head 16 --block-size 512 \
  --max-iters 10000 --batch-size 1 \
  --warmup-iters 1000 --lr-decay-iters 10000 \
  --grow-mult 32 --init-from <prev> \
  --no-freeze-attn --route-aware --route-alpha 0.9 \
  --run-name "k25w1024-<tag>"
```

Observed grow header (confirms the mask and the frozen path):

```
route-aware: prefix mask 8192..10240 | loss = 0.9*prefix + 0.1*full
growth: 128 -> 160 mult (+2048 neurons/head trainable) | old neurons + embed + lm_head
        frozen (bit-exact via step-end restore) | attn parameter-free (bdh; freeze flags inert)
```

## Measured Preflight (2026-10-14, host `spark-d1da`)

Short training runs, `max-iters` 20 and 70 on the same configuration, so the per-step cost is
the difference divided by 50 (startup, dataset and checkpoint I/O cancel out).

| Run | compile | iters | wall (s) | **ms/step** |
|---|---|---:|---:|---:|
| base | no | 20 | 59.62 | — |
| base | no | 70 | 92.23 | **652** |
| grow (mult 160) | no | 20 | 101.40 | — |
| grow (mult 160) | no | 70 | 183.02 | **1632** |
| base | yes | 20 | 64.87 | — |
| base | yes | 70 | 86.72 | **437** |
| grow (mult 160) | yes | 20 | 108.25 | — |
| grow (mult 160) | yes | 70 | 138.02 | **595** |

- `torch.compile` gives **1.49×** on the base and **2.74×** on the grow phase. Which setting the
  bridge will use is *not* settled here: see the compile-setting note above — Sonde A ran with
  dynamo disabled and K20's setting is undocumented in the repository. The tables below assume
  the compiled numbers; if the protocol is fixed to uncompiled for K20 comparability, the wall
  clock roughly doubles.
- A real grow phase at mult 160 is therefore ~5954 s ≈ **1.65 h** for 10,000 steps.

## Resource Projection

### Checkpoint storage

Summing the parameter model over mult 128…896 (25 values, step 32) gives 40.28 G parameters
across all phases; at 12 bytes/parameter and two checkpoints (`best` + `last`) per phase:

| Item | Value |
|---|---:|
| Σ parameters, all phases | 40,278,425,600 |
| per checkpoint copy | ~483 GB |
| `best` + `last`, all phases | **~967 GB** |
| final phase alone (mult 896) | 33.83 GB × 2 = 67.7 GB |

**~1 TB on a 3.5 TB disk: fits, with ~3.5× headroom — but the margin must be monitored per
phase.**

### Wall clock

Measured, then extrapolated linearly in width (the model is linear in `mult`):

| Item | Basis | Estimate |
|---|---|---|
| base phase, 150,000 steps, batch 4, compiled | extrapolated from 437 ms/step | **~3 days** |
| 24 grow phases, batch 1, compiled | 595 ms/step at width 10240, scaled by width | **~5–6 days** |
| per-phase instruments (routdiag, P5, joint/routed) | K20 analogue | ~0.5–1 day total |
| final 25×25 matrix, 200 crops/domain | K20 took 16.4 h at W512 | **~2–3 days (extrapolated)** |
| **total** | | **~11–13 days** |

### Unified memory — **gate run at full width: PASS**

A full-width training run was executed on 2026-10-14 (`mult 896`, 2.82 B parameters,
compiled, batch 1, `block 512`):

| Quantity | Value |
|---|---|
| `run_exit` | **0** |
| **peak GPU/unified memory** | **~82 GB** (independent `nvitop` reading) |
| host total | 121.7 GiB |
| reserve at peak | **~40 GiB** |
| wall | 12:07 for 2 iterations (≈11 min of that is `torch.compile`) |

**Reading correction (v0.3).** The gate script also sampled `/proc/<pid>/VmHWM` and reported
11.12 GiB. That figure is **wrong as a GPU-memory measure**: PyTorch allocated the weights
through the VMM allocator (`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`), whose mappings
are not all reflected in resident-set accounting, and the script's sampler also latched onto
the wrapper PID. The independent `nvitop` reading of **~82 GB** is the trustworthy number, and
it confirms the v0.2 projection of ~85–90 GB rather than refuting it.

The gate passes with roughly 40 GiB of headroom. It is **not** comfortable enough to skip
per-phase monitoring: the OS and other processes share this memory, and later phases are
wider still than mult 896 only in their accumulated checkpoints, not in model size.

## Gates

### Gate W-PASS (bridge works)
- **Preflight gate:** a full-width (mult 896) training step completes.
  → **Satisfied 2026-10-14**: `run_exit=0`, peak ~82 GB, ~40 GiB reserve.
- **P5:** 24/24 transitions bit-exact (absolute stop-gate).
- **Final routing:** ≥95% own-route accuracy.
- **First prose retention:** |ΔPPL| ≤ 0.08.
- **Cost:** each phase ≤1.5× its projected wall time; no superlinear cost curve over the 24 positions.
- **Resume:** a phase-boundary resume reproduces bit-identical continuation.

### Gate W-PARTIAL
- P5 holds, but routing, memory or cost degrade → PoC scope adjusted (smaller width, larger
  growth quanta, or a capped ladder).

### Gate W-FAIL
- P5 fails, or the memory reserve collapses in later phases → mechanism does not scale as
  theorised; F-V9/masking at greater depth must be re-audited before any PoC.

## Risk Assessment

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Unified memory pressure in later phases | Medium | High | Peak monitor per phase; ~40 GiB reserve at the widest measured point |
| Disk growth faster than projected | Low | Medium | Per-phase disk check; ~1 TB projected on 3.5 TB |
| P5 breaks at W1024 | Low | Fatal | P5 at every transition; stop immediately |
| Cost exceeds projection | Medium | High | Phase 1 telemetry; stop rule at 1.5× |
| Host toolchain regression (`python3-dev`) | Low | Medium | Verified installed; compile test in the checklist |
| Power event mid-phase | Low | Medium | Phase-boundary resume; checkpoints survive |

## Pre-registered Predictions

- **P-W1 (P5 size-neutral):** P5 stays bit-exact on all 24 transitions at W1024. Expected PASS
  since F-V9 is structural, but this remains the load-bearing gate.
- **P-W2 (routing at width):** final routing accuracy ≥95%. Falsifier: below that → the
  growth quantum is width-bound; the PoC needs larger quanta or a smaller base width.
- **P-W3 (retention at width):** first prose retention |ΔPPL| ≤ 0.08. Falsifier: above that →
  accumulated drift is width-sensitive; the PoC needs periodic re-anchor steps.
- **P-W4 (cost sub-quadratic):** per-phase GPU-seconds stay sub-quadratic in mult across the
  24 positions. Falsifier: superlinear → regroup the ladder.
