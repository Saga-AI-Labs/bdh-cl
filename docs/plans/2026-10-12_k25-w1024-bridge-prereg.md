# K25/W1024 Bridge — Scaling Probe at Double Width

**Status:** DRAFT v0.2 · drafted 2026-10-12 · **measured 2026-10-14** · Quinn
**Purpose:** Isolate whether the BDH mechanism (storage exact, serving degraded, routing repaired) holds at `n_embd=1024` (`n_head=16`) with the same K25 territory mix.
**Hardware:** DGX Spark `spark-d1da` (192.168.178.52), GB10, 3.5 TB free NVMe

> **v0.2 correction (2026-10-14):** every parameter, checkpoint and timing figure in v0.1 was
> arithmetic, and the arithmetic was wrong by roughly a factor of nine. Measured values now
> replace them; the v0.1 estimates are kept in the changelog at the bottom of this file.

---

## Why This Bridge

The K20/W512 ladder (2× multi-seed) established:
- K3 routing: 99.14–99.18% PASS
- K4 retention: PASS (median ratio 1.0000, max 1.0429)
- Joint/routed gap: 6.76–6.86×
- P5 bit-exact preservation: 25/25 phases PASS

All at `n_embd=512`, `n_head=8`, `head_dim=64`.

**Open question:** does the mechanism survive when the base architecture is wider? This is a
**pure scaling probe** — same territories, same data windows, same protocol, same instrument
suite. The only changed variable is `n_embd` (512→1024) with `n_head` (8→16) so that
`head_dim` stays 64.

|---|---|---|
| `n_embd` | 512 | 1024 |
| `n_head` | 8 | 16 |

### Parameter model (validated against three measurements)

```
params = 3·mult·d² + 2·vocab·d      (d = n_embd, vocab = 256, byte-level)
```

| Config | Formula | Measured | Match |
|---|---:|---:|---|
| W512, mult 896 (K20 prereg table) | 704,905,216 | 704,905,216 | exact |
| W1024, mult 128 (v0.2 smoke) | 403,177,472 | 403,177,472 | exact |
| W1024, mult 160 (v0.2 smoke) | 503,840,768 | 503,840,768 | exact |

The formula is exact on all three, so the extrapolated end-phase value is trustworthy:

| +1 | 160 | 10240 | 503,840,768 |
| … | … | … | … |

## Training Protocol

| Parameter | Value |
|---|---|
| steps per phase | 10,000 |
| `--grow-mult` | 32 |
| `--route-aware` / `--route-alpha` | on / 0.9 |
| `--no-freeze-attn` | on (inert for BDH: attention is parameter-free) |
| optimizer | fresh per phase |
| restore | F-V9 step-end |
| router | likelihood scan (`eval_router`) |
| eval window | 128 |
| crops per domain | 200 |
| `--block-size` | 512 |
| batch | 1 (grow phases), as K20 |

**No hyperparameter search. No protocol drift from K20.**

Grow-phase invocation (verbatim from the v0.2 smoke, which ran clean):

```
.venv/bin/python -m pipeline.run train --model bdh --dataset textmix \
  --text-mix "legal:data/textmix2/legal.txt" --text-mix-mb 30 \
  --n-embd 1024 --n-head 16 --block-size 512 \
  --max-iters 10000 --batch-size 1 \
  --warmup-iters 1000 --lr-decay-iters 10000 \
  --grow-mult 32 --init-from <prev> \
  --no-freeze-attn --route-aware --route-alpha 0.9 \
  --run-name "k25w1024-<tag>"
```

Observed grow header (confirms the mask and the frozen path):

```
route-aware: prefix mask 8192..10240 | loss = 0.9*prefix + 0.1*full
growth: 128 -> 160 mult (+2048 neurons/head trainable) | old neurons + embed + lm_head
        frozen (bit-exact via step-end restore) | attn parameter-free (bdh; freeze flags inert)
```

## Measured Preflight (2026-10-14, host `spark-d1da`)

Four short training runs, `max-iters` 20 and 70 on the same configuration, so the per-step
cost is the difference divided by 50 (startup, dataset and checkpoint I/O cancel out).

| Run | compile | iters | wall (s) | **ms/step** |
|---|---|---:|---:|---:|
| base | no | 20 | 59.62 | — |
| base | no | 70 | 92.23 | **652** |
| grow (mult 160) | no | 20 | 101.40 | — |
| grow (mult 160) | no | 70 | 183.02 | **1632** |
| base | yes | 20 | 64.87 | — |
| base | yes | 70 | 86.72 | **437** |
| grow (mult 160) | yes | 20 | 108.25 | — |
| grow (mult 160) | yes | 70 | 138.02 | **595** |

- `torch.compile` gives **1.49×** on the base and **2.74×** on the grow phase. **The bridge runs
  compiled**, matching K20.
- A real grow phase at mult 160 is therefore ~5954 s ≈ **1.65 h** for 10,000 steps.

## Resource Projection (replaces the v0.1 arithmetic)

### Checkpoint storage

Summing the parameter model over mult 128…896 (25 values, step 32) gives 40.28 G parameters
across all phases; at 12 bytes/parameter and two checkpoints (`best` + `last`) per phase:

| Item | Value |
|---|---:|
| Σ parameters, all phases | 40,278,425,600 |
| per checkpoint copy | ~483 GB |
| `best` + `last`, all phases | **~967 GB** |
| final phase alone (mult 896) | 33.8 GB × 2 = 67.6 GB |

**~1 TB on a 3.5 TB disk: fits, with ~3.5× headroom — but the margin must be monitored per
phase.** This is 24× the v0.1 estimate.

### Wall clock

Measured, then extrapolated linearly in width (the model is linear in `mult`):

| Item | Basis | Estimate |
|---|---|---|
| base phase, 10,000 steps, compiled | 437 ms/step | **1.2 h** |
| 24 grow phases, compiled | 595 ms/step at width 10240, scaled by width | **~5–6 days** |
| per-phase instruments (routdiag, P5, joint/routed) | K20 analogue | ~0.5–1 day total |
| final 25×25 matrix, 200 crops/domain | K20 took 16.4 h at W512 | **~2–3 days (extrapolated)** |
| **ladder total** | | **~8–10 days** |

**Not included: the W1024 base checkpoint does not exist yet.** K20 initialised from the
already-trained A1-K5 bases. The bridge needs its own W1024 base trained with the same base
protocol (prose + multilingual, `mult 128`). At the measured compiled rate, a Sonde-C0-style
140–150k-step base is roughly **2 days** on this host. That cost is additive and must be
scheduled before phase 1.

### VRAM / unified memory — **open risk, hard gate**

K20's measured worst case at W512/mult 896 (704.9 M params) was **21,934 MiB** peak on a
24 GB card. The bridge's final phase has 4× those parameters (2.82 B). Scaling the measured
per-parameter footprint gives an order of **~85–90 GB**, against 128 GB of unified memory
shared with the OS.

That is plausible but **not measured**, and it is the single most likely reason the ladder
fails late rather than early. A full-width step test is therefore a **launch-blocking gate**,
not a formality. (v0.1 claimed <3 GB "trivial" — that claim was wrong and is retracted.)

## Gates

### Gate W-PASS (bridge works)
- **Preflight gate (new, v0.2):** a single training step at mult 896 completes and the peak
  memory is recorded with ≥15 GB headroom.
- **P5:** 24/24 transitions bit-exact (absolute stop-gate).
- **Final routing:** ≥95% own-route accuracy.
- **First prose retention:** |ΔPPL| ≤ 0.08.
- **Cost:** each phase ≤1.5× its projected wall time; no superlinear cost curve over the 24 positions.
- **Resume:** a phase-boundary resume reproduces bit-identical continuation.

### Gate W-PARTIAL
- P5 holds, but routing, memory or cost degrade → PoC scope adjusted (smaller width, larger
  growth quanta, or a capped ladder).

### Gate W-FAIL
- P5 fails, or the full-width memory gate cannot be met → mechanism does not scale as
  theorised; F-V9/masking at greater depth must be re-audited before any PoC.

## Risk Assessment (v0.2)

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Full-width (mult 896) exceeds unified memory | **Medium** | Fatal | Preflight gate above; if it fails, cap the ladder's final mult |
| Disk growth faster than projected | Low | Medium | Per-phase disk check; ~1 TB projected on 3.5 TB |
| P5 breaks at W1024 | Low | Fatal | P5 at every transition; stop immediately |
| Cost exceeds projection | Medium | High | Phase 1 telemetry; stop rule at 1.5× |
| Host toolchain regression (`python3-dev`) | Low | Medium | Verified installed; compile test in the checklist |
| Power event mid-phase | Low | Medium | Phase-boundary resume; checkpoints survive |

## Pre-registered Predictions

- **P-W1 (P5 size-neutral):** P5 stays bit-exact on all 24 transitions at W1024. Expected PASS
  since F-V9 is structural, but this remains the load-bearing gate.
- **P-W2 (routing at width):** final routing accuracy ≥95%. Falsifier: below that → the
  growth quantum is width-bound; the PoC needs larger quanta or a smaller base width.
- **P-W3 (retention at width):** first prose retention |ΔPPL| ≤ 0.08. Falsifier: above that →
  accumulated drift is width-sensitive; the PoC needs periodic re-anchor steps.
- **P-W4 (cost sub-quadratic):** per-phase GPU-seconds stay sub-quadratic in mult across the
  24 positions. Falsifier: superlinear → regroup the ladder.
